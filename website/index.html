OpenCaP

How open-weight models fail at writing robot code, and the smallest fix for each failure

Twenty-one open-weight models write programs that control a robot. For every program that fails, we find the smallest edit that makes it work, keeping the model's own code, and record what that edit had to fix.

Author
Sajjad Pakdamansavoji
Affiliation

Code Write-up BibTeX

Language models can write Code-as-Policies programs that drive a robot, and success rate is how they are usually compared. Success rate says how often a program fails but not why. OpenCaP takes every failing program from a grid of 21 open-weight models, four manipulation tasks in CaP-X and three levels of robot API, repairs each with the smallest edit that makes it work, and tags each cause the repair had to fix.

The level of the API decides what goes wrong. With high-level helpers, failures are mostly not about robotics: an uncalled function, a shadowed primitive, a missing final action, the wrong object. Remove the helpers, leaving only perception, inverse kinematics and the gripper, and coordinate-frame errors jump from 4% to 47% of failing programs, misread API calls from 26% to 60%, and the larger models lose their advantage: their failing programs carry about twice as many defects as before.

How OpenCaP works

Each failing program is treated as evidence of a specific mistake, not as a zero. The repair is the measurement: the smaller the edit that makes a program work, the closer the model was, and the edit itself names what was wrong.

  1. Step 01

    Run the grid

    Every model writes one program per task and API level, run on 30 fixed scenes. S1 offers helpers such as get_object_pose and goto_pose. S3 keeps only perception (SAM3, Molmo, Contact-GraspNet), solve_ik, move_to_joints and the gripper. S4 also removes the worked example.

  2. Step 02

    Repair minimally

    Each failing program gets the smallest edit that makes it pass, keeping the model's code. A repair is accepted when no scene fails in all k draws, with k calibrated per task on the task's own reference program. Workarounds any correct program would need are shared and never counted as defects.

  3. Step 03

    Tag the cause

    Each repair gets one tag per distinct cause, in six families: syntax, structure, interface, semantic, trajectory and frame. 70 failing programs at S1 and 169 at S3/S4 are tagged, 116 of them against a verified repair.

Lowering the API changes what fails

At S1 the API returns world poses, so frame errors almost never happen. At S3 and S4 the model must turn camera-frame detections into world coordinates itself, and that is where it breaks. The rise holds on every task, and with unverified records removed.

The scale advantage disappears

With helpers, a larger model's failing programs are cleaner: defects per failing program fall from 4.2 at 2B and below to 1.5 at 7B and above. Without them, every size band sits between 3.2 and 4.6. Frame errors appear for 19 of the 21 models at S3/S4, against 3 of 21 at S1; the two exceptions are the smallest models, whose programs fail before reaching any coordinate math.

Checks and limits

The token cap does not explain the failures. Raising it from 2,048 to 8,192 tokens fixes no failure of a 12B or larger model: two models loop on one line at any budget, and another completes and still crashes. No program cheats. The observation also exposes object poses, and a scan of all 5,040 S3/S4 episodes found no program reading them.

The tags come from language models, not people. Claude Opus 5 tagged every program against its repair. An independent rater from a different model family, GPT-6 Astra, blind to the question, re-tagged a 60-program sample: per-family agreement is κ 0.82 for frame and 0.87 for interface, and both contrasts reproduce in its own labels. The size of the defect-count gap moves between raters, so the family contrasts are the stronger result. No human has rated the packet yet; it ships with the code, ready for one.

These are failing programs only: the counts describe what goes wrong, not how often programs fail.

Reproducing

Every number on this page is regenerated on a CPU from the tags and repairs in the GitHub repository, for example python scripts/cross_tier_report.py --no-truncated. The method, all tables and the limitations are in the write-up.

Built on

CaP-X, with models served by vLLM and perception from SAM3, Molmo and Contact-GraspNet.
